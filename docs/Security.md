# Security – safety and risk controls

Rules for secrets, authentication and untrusted input, and an honest list of
what this project does not protect against. Rules marked with a phase are
implemented in that phase; the rest apply from the first commit.

## 1. Secrets

- The repository contains no secret. `appsettings.json` holds only hosts, ports,
  timeouts, file paths and the non-secret settings of the optional result
  publisher. Its API key is read from the `FabTrace__ApiKey` environment variable.
- If a secret is ever needed (for example a token for a factory server), it
  comes from an environment variable or .NET user-secrets, never from a file in
  the repository.
- `.gitignore` excludes databases (`*.db`), `logs/`, `data/` and `models/`. A
  database holds password hashes and an audit trail and is never committed.
- Passwords, hashes and salts never appear in logs, exception messages, the
  audit trail, test output or chat.
- GitHub Actions (phase 4) needs no secret. The workflow declares
  `permissions: contents: read`.

## 2. Authentication and authorisation (phase 3)

- **Hashing:** PBKDF2 with HMAC-SHA256 from the .NET base library
  (`Rfc2898DeriveBytes.Pbkdf2`). No third-party crypto package.
- **Salt:** random, per user, from `RandomNumberGenerator`.
- **Iterations:** 600,000 (`PasswordSecurity.DefaultIterations`), stored per
  user so the cost can be raised without resetting passwords.
- **Comparison:** `CryptographicOperations.FixedTimeEquals`, so timing does not
  leak how much of a hash matched.
- **Lockout:** an account locks for 15 minutes after 5 failed logins. Failed
  logins are written to the audit trail.
- **Roles:** Operator, Engineer, Admin. A permission is checked in the service
  that performs the action, not only by hiding a button.
- **Sign-off:** a recipe change requires the user to re-enter their password and
  give a reason, even when already logged in. The change and the audit entry are
  saved in one transaction.
- **Seeded accounts:** a new database is seeded with one user per role. These
  are development-only accounts: their passwords are in the seed
  (`DatabaseInitializer`), the README and the demo script. That is not
  acceptable on a real station; see section 6.
- **No automatic sign-in:** the app starts at the login dialog. A lot cannot be
  opened and an AI review cannot be submitted without a signed-in user, so both
  are always attributed to a person.
- **Password entry:** passwords are typed into masked password boxes and the
  view model clears its copy after each attempt.
- Users are deactivated, not deleted, so audit entries always keep their owner.

## 3. Audit trail (phase 3)

- Insert-only: no code path updates or deletes an audit row.
- Records who, what, when, old value, new value and, for signed changes, the reason.
- Never stores a password or a hash as an old or new value.

## 4. Untrusted input

Everything that arrives from outside the process is validated before use.

| Source | Control |
|---|---|
| Database queries | EF Core LINQ or parameterised SQL only. Never build SQL by joining strings |
| SCPI replies | Maximum line length, read timeout, numeric parse with invariant culture, finite-number check |
| Modbus values | Range-checked before use; a failed or short read is a fault, not a zero |
| Barcodes (phase 4) | Length limit and allowed-character check |
| User text (names, reasons) | Length limit; displayed as text, never interpreted |
| File paths | Generated by the app from ids and timestamps; never taken from input |
| Images and model files (phase 5) | Loaded only from the app's own folders; a fixed model version label is stored with every AI verdict |

## 5. Network

- The simulator and its test hosts bind to `127.0.0.1` only.
- The app makes no outbound connection except to the configured PLC, instrument
  and camera addresses. The optional HTTP result publisher is switched off by
  default.
- Dependencies are checked with `dotnet list package --vulnerable` before each
  phase is closed, and in CI from phase 4.

## 6. Honest limits

These are known and deliberate. They must not be hidden or described as solved.

- **Modbus TCP and raw SCPI have no authentication or encryption.** That is how
  the protocols work; real machines isolate them on a machine network.
- **The software emergency stop is not a safety function.** On a real machine
  the e-stop is hard-wired through a safety relay; software only observes it.
- **The SQLite file is not encrypted**, and anyone with file access can edit it,
  including the audit trail. The audit trail is insert-only at the application
  level only.
- **The audit trail and sign-off are modelled on regulated-industry practice**
  but are not certified against any standard.
- **The seeded accounts have published passwords.** This suits a demonstration
  and nothing else.
- **No real hardware is involved**, so nothing here has been tested against real
  device behaviour, electrical noise or timing.
